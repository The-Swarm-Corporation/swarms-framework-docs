## Overview

The `ModelRouter` is an intelligent routing system that automatically selects and executes AI models based on task requirements. It leverages a function-calling architecture to analyze tasks and recommend the optimal model and provider combination for each specific use case.

Each step makes two LLM calls:

1. A routing call to `gpt-4o` with `response_format=ModelOutput`. The reply is parsed into a `ModelOutput` that names the model, provider, rewritten task, `max_tokens`, `temperature`, and `system_prompt` to use.
2. An execution call to `{provider}/{model}` through LiteLLM, using the settings from that reply.

## Key Features

- Dynamic model selection based on task complexity and requirements
- Multi-provider support (OpenAI, Anthropic, Google, etc.)
- Sequential, batch, and thread-pool concurrent execution
- Optional multi-loop refinement, where each step's output becomes the next step's task
- OpenTelemetry tracing: each `run()` is a `ModelRouter.run` span, and `concurrent_run()` carries the tracing context into its worker threads (see [Telemetry](/deployment/telemetry))

## Attributes

<ParamField path="system_prompt" type="str" default="model_router_system_prompt">
  System prompt for the routing call. It replaces the built-in selection guidance, so describe the models you want the router to choose from. It does not reach the selected model; that model gets the `system_prompt` written in the routing reply.
</ParamField>

<ParamField path="max_tokens" type="int" default="4000">
  Stored as `router.max_tokens` and shown in `repr()`. Neither LLM call reads it: the execution call uses the `max_tokens` from the routing reply.
</ParamField>

<ParamField path="temperature" type="float" default="0.5">
  Temperature for the routing call. The execution call uses the `temperature` from the routing reply.
</ParamField>

<ParamField path="max_workers" type="int | str" default="10">
  Thread count for `concurrent_run()`. Use `"auto"` for `os.cpu_count()`.
</ParamField>

<ParamField path="api_key" type="str" default="None">
  Accepted but unused. Set provider keys as environment variables instead.
</ParamField>

<ParamField path="max_loops" type="int" default="1">
  Maximum number of steps per `run()`. Each step's output becomes the next step's task, and the loop stops early if a step returns its input unchanged.
</ParamField>

Extra positional and keyword arguments are accepted and ignored.

## `ModelOutput`

The schema the routing call must return. Import it from `swarms.structs.model_router`.

```python
class ModelOutput(BaseModel):
    rationale: Optional[str]
    model: Optional[str]
    provider: Optional[str]
    task: Optional[str]
    max_tokens: Optional[int]
    temperature: Optional[float]
    system_prompt: Optional[str]
```

## Methods

### step()

Runs a single routing step. It sends the task to the routing model, parses the JSON reply into a `ModelOutput`, prints the decision, then runs the rewritten task on `{provider}/{model}` and prints the output. `run()` calls this internally in a loop up to `max_loops` times.

```python
def step(self, task: str) -> str
```

**Parameters:**
- `task` (str): The task to be executed

**Returns:** `str` - The selected model's output

**Raises:** `pydantic.ValidationError` if the routing reply does not parse as a `ModelOutput`. Errors from the execution call propagate unchanged.

### run()

Runs `step()` up to `max_loops` times, feeding each output back in as the next task. Recorded as a `ModelRouter.run` trace span when telemetry is enabled. Calling the router directly, `router(task)`, does the same thing.

```python
def run(self, task: str) -> str
```

**Parameters:**
- `task` (str): The task to be executed

**Returns:** `str` - The result of task execution

### batch_run()

Executes multiple tasks sequentially with result aggregation.

```python
def batch_run(self, tasks: list) -> list
```

**Parameters:**
- `tasks` (list): List of task strings to be executed

**Returns:** `list` - List of results, one for each task

**Raises:** `RuntimeError` wrapping the first failure.

### concurrent_run()

Runs `run()` once per task on a thread pool of `max_workers` threads. The pool carries the caller's tracing context into each thread, so every task's span joins the caller's trace.

```python
def concurrent_run(self, tasks: list) -> list
```

**Parameters:**
- `tasks` (list): List of task strings to be executed

**Returns:** `list` - Results in task order

**Raises:** `RuntimeError` wrapping the first failure.

### async_run()

<Warning>
`async_run()` is currently broken and should not be used. Its implementation is `return asyncio.create_task(self.run(task, *args, **kwargs))`, but `run()` is a plain **sync** `def` -- so `self.run(...)` executes eagerly (blocking the event loop) and returns a plain `str` before `asyncio.create_task()` ever sees it. Passing that string to `create_task()` raises `TypeError: a coroutine was expected`, which `async_run()` catches and re-raises as `RuntimeError: Async execution failed: ...`. Every `await router.async_run(...)` call site fails. Use the synchronous `run()` (optionally wrapped in `asyncio.to_thread()` from an async context) or `concurrent_run()` / `batch_run()` for parallel execution instead.
</Warning>

Documented (broken) signature:

```python
async def async_run(self, task: str) -> asyncio.Task
```

**Working alternative from an async context:**

```python
import asyncio
from swarms import ModelRouter

router = ModelRouter()

async def run_task(task: str):
    # Keeps the blocking run() call off the event loop.
    return await asyncio.to_thread(router.run, task)

result = asyncio.run(run_task("Analyze the sentiment in this feedback"))
```

## Usage Examples

### Basic Usage

```python
from swarms import ModelRouter

router = ModelRouter()

# Simple text analysis
result = router.run("Analyze the sentiment and key themes in this customer feedback")

# Complex reasoning task
complex_result = router.run("""
Evaluate the following business proposal:
- Initial investment: $500,000
- Projected ROI: 25% annually
- Market size: $2B
- Competition: 3 major players
Provide detailed analysis and recommendations.
""")
```

### Batch Processing

```python
from swarms import ModelRouter

router = ModelRouter()

# Multiple analysis tasks
tasks = [
    "Analyze Q1 financial performance",
    "Predict Q2 market trends",
    "Evaluate competitor strategies",
    "Generate growth recommendations"
]

results = router.batch_run(tasks)

# Process results
for task, result in zip(tasks, results):
    print(f"Task: {task}\nResult: {result}\n")
```

### Concurrent Execution

```python
from swarms import ModelRouter

router = ModelRouter()

# Define multiple concurrent tasks
analysis_tasks = [
    "Perform technical analysis of AAPL stock",
    "Analyze market sentiment from social media",
    "Generate trading signals",
    "Calculate risk metrics"
]

# Execute tasks concurrently
results = router.concurrent_run(analysis_tasks)

# Process results with error handling
for task, result in zip(analysis_tasks, results):
    try:
        processed_result = process_analysis(result)
        save_to_database(processed_result)
    except Exception as e:
        log_error(f"Error processing {task}: {str(e)}")
```

### Asynchronous Execution

`async_run()` is currently broken (see the [Warning above](#async_run)). To call `ModelRouter` from an async context without blocking the event loop, offload the synchronous `run()` to a thread with `asyncio.to_thread()`:

```python
import asyncio
from swarms import ModelRouter

async def process_data_stream():
    router = ModelRouter()
    tasks = []
    async for data in data_stream:
        tasks.append(asyncio.to_thread(router.run, f"Process data: {data}"))

    results = await asyncio.gather(*tasks)
    return results

# Usage in async context
async def main():
    results = await process_data_stream()
```

## Available Models and Use Cases

The default routing prompt embeds these recommendations. The routing model can still name any model.

| Model | Provider | Best for |
|-------|----------|----------|
| gpt-5.4 | openai | Simple queries, basic text generation, quick responses |
| gpt-4-turbo | openai | Complex tasks, up-to-date knowledge, long context |
| gpt-3.5-turbo | openai | Chat applications, content generation, basic assistance |
| o3-mini | groq | Basic completion, simple classification, constrained environments |
| deepseek-reasoner | deepseek | Complex problem solving, logical reasoning, mathematical analysis |
| claude-3-5-sonnet | anthropic | Creative writing, detailed analysis, nuanced responses |
| claude-3-opus | anthropic | Research, complex analysis, technical writing, code generation |
| gemini-pro | google | Multimodal tasks, code generation, creative content |
| mistral-large | mistral | General purpose tasks, code assistance, content generation |

## Performance Optimization Tips

1. **Token Management**
   - The routing reply sets `max_tokens` for each execution call, so ask for a limit in your `system_prompt` if you need one
   - Raise `max_loops` only when refinement is worth the extra calls; each step makes two LLM calls

2. **Concurrency Settings**
   - Adjust `max_workers` based on system resources
   - Use `"auto"` workers for optimal CPU utilization
   - Monitor memory usage with large batch sizes

3. **Temperature Tuning**
   - Lower (0.1-0.3) for factual/analytical tasks
   - Higher (0.7-0.9) for creative tasks
   - Mid-range (0.4-0.6) for balanced outputs

4. **System Prompts**
   - A custom `system_prompt` replaces the routing guidance, so list the models and providers you want chosen
   - Include relevant context
   - Define clear output formats
